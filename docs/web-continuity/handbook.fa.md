# دفترچهٔ فنی اجرای وب مستقل زیباشی

**نسخهٔ ۱٫۰ — ۱۸ نوامبر ۲۰۲۶ — برنامهٔ اجرا و پذیرش**

مخاطب: مدیر کسب‌وکار، مجری نرم‌افزار، مسئول زیرساخت، حسابدار و مسئول ارسال.

مبنای بررسی کد: `a4e27a86a9c67b3d5bd8a99f80d41f7d29febf3e`. آخرین مدرک انتشار محلی، نسخهٔ `customer-finance-0b6989356276` با ۱۵۹۳ بررسی API و ۱۵۰ آزمون Application است؛ این اعداد گواه آماده‌بودن سایت جدید نیستند. اندازهٔ جامعهٔ فعال، حدود ۱۰۰۰ مشتری، از درخواست مدیر گرفته شده و تعداد کاربر هم‌زمان اندازه‌گیری نشده است. زیرساخت زنده در این بررسی دوباره ممیزی نشده است.

این سند مجوز جابه‌جایی production یا اعلام آماده‌بودن وب نیست. تغییرات این مرحله فقط مستندات است. هر قابلیت وب تا ثبت شاهد آزمون و امضای مرحله «برنامه‌ریزی‌شده» است. همهٔ مبالغ فروش به تومان‌اند و زمان‌های ثبت، UTC با نمایش تهران هستند.

## ۱. هدف و تعریف موفقیت

هدف، ادامهٔ فروش و عملیات زیباشی هنگام قطع تلگرام و قطع ارتباط بین‌الملل، در شرایط برقرار بودن اینترنت داخلی است. مشتری باید بتواند وارد همان حساب قبلی شود، عطر و موجودی بخرد، فاکتور و رسید ببیند، آدرس ثبت کند و بسته را پیگیری کند؛ کارکنان نیز حسابداری و دکانت و آماده‌سازی را ادامه دهند.

معیار نهایی: ارتباط خارجی محیط آزمایش عملاً بسته شود؛ کاربر تازه و کاربر قبلی روی شبکه‌های داخلی وارد شوند؛ خرید، رزرو، فاکتور، رسید، تأیید پرداخت، بسته و رهگیری کامل شوند؛ سپس اتصال برگردد و پیام‌های عقب‌افتاده بدون سفارش یا فاکتور دوم تحویل شوند. قطع کامل دسترسی داخلی کاربر، اختلال خود بانک یا پیامک، یا خرابی هم‌زمان همهٔ مراکز میزبانی با صرف ساخت سایت رفع نمی‌شود.

اصل اجرا: فروش فعلی و دادهٔ واقعی مرجع‌اند. ساخت وب در محیط جدا آغاز می‌شود. تغییر بزرگ هسته، تغییر دیتابیس، انتقال سرور و انتشار عمومی در یک نوبت انجام نمی‌شوند. هدف کاهش اختلال و اثبات کنترل آن است؛ وعدهٔ قطعیِ توقف صفر پیش از اندازه‌گیری و تمرین مهاجرت معتبر نیست.

## ۲. آنچه امروز قابل استفاده است و شکاف‌ها

| موضوع | مبنای مشاهده‌شده | کار لازم |
|---|---|---|
| داده و عملیات | .NET 10، EF Core، SQL Server؛ مشتری، لیست، موجودی، سفارش، پرداخت و ارسال | حفظ شناسه‌ها و استخراج قواعد مشترک به عملیات مستقل از کانال |
| رابط وب | پنل اولیهٔ `/admin` با کلید مدیریتی | رابط مشتری و کارکنان با ورود و نقش مستقل؛ پنل اولیه معادل ERP کامل وب نیست |
| API | APIهای عمدتاً مجاز برای Admin و TelegramBot و N8n | API مخصوص مشتری با بررسی مالکیت رکورد و نشست امن |
| قوانین تازه | بخش‌هایی در `TelegramWebhookController.*` و بخش‌هایی در سرویس‌ها | فهرست تطبیق و استفادهٔ سایت و ربات از همان عملیات تجاری |
| رسانه | بسیاری از تصاویر مرجع با Telegram FileId و بخشی از مدارک در artifact یا payload | نسخهٔ مستقل فایل و نگاشت دقیق به رکورد و نسخه |
| اعلان | Outbox و رسید و retry برای تلگرام و n8n | رویداد تجاری مستقل و رسید جداگانه برای هر کانال |
| استقرار | مستندات مقصد فرانسه و SQL Server Express | اندازه‌گیری تازه، طراحی مقصد ایران و بازیابی مستقل داخلی |
| هویت | CustomerId مشترک با موبایل و شناسه‌های تلگرام | اثبات مالکیت حساب و موبایل، رفع ابهام و بازیابی مستقل |

ترتیب اعتبار شواهد: پیکربندی و رفتار واقعاً بررسی‌شدهٔ نسخهٔ فعال، سپس کد همان نسخه، سپس آزمون، سپس مستند قدیمی. برخی مستندات قدیمی از قابلیت‌های تازه عقب‌اند؛ برای مثال سند قدیمی نرخ درهم از نبود دریافت خودکار می‌گوید ولی کد فعلی سرویس دریافت خودکار دارد. هر اختلاف باید در مرحلهٔ P0 به تصمیم و آزمون تبدیل شود.

## ۳. تصمیم‌های معماری

| شناسه | تصمیم پیشنهادی | دلیل و قید |
|---|---|---|
| ADR-01 | یک هستهٔ تجاری و یک مرجع نوشتن | سایت و تلگرام حساب یا موجودی مستقل نسازند |
| ADR-02 | نگهداری .NET و SQL Server فعلی در شروع | کاهش خطر بازنویسی هم‌زمان و حفظ قواعد آزموده‌شده |
| ADR-03 | رابط Next.js/TypeScript به شکل PWA | تجربهٔ موبایل و امکان نصب و صفحات عمومی؛ قفل‌شدن عملیات به جاوااسکریپتِ cache شده پذیرفته نیست |
| ADR-04 | هسته، داده و فایل ضروری در ایران برای مرحلهٔ استمرار داخلی | صفحهٔ داخلی با دیتابیس خارجی هدف قطعی بین‌الملل را برآورده نمی‌کند |
| ADR-05 | اتصال تلگرام از طریق درگاه مستقل خارج ایران | دسترسی شبکه‌ای تلگرام از هسته جدا شود؛ درگاه اجازهٔ صدور مستقل مالی نگیرد |
| ADR-06 | فایل خصوصی مستقل و دانلود مجاز | فایل به محصول و مالک و نسخه متصل، و Telegram FileId صرفاً شناسهٔ کانال باشد |
| ADR-07 | استخراج تدریجی عملیات از مسیر ربات | هر عملیات ابتدا آزمون تطبیق بگیرد، سپس ربات و وب به همان سرویس متصل شوند |
| ADR-08 | کلید مدیریتی فعلی فقط سرویس‌به‌سرویس | کلید عمومی مدیریت یا ربات وارد bundle، localStorage یا فرم ورود مشتری نشود |

SQL و زیرساخت اجرایی در مرحلهٔ اول حفظ می‌شوند. انتخاب Edition جدید SQL، سرویس ذخیره‌سازی، پیامک، میزبانی و مسیر پشتیبان پس از ممیزی و آزمایش تعیین می‌شود. این سند نیاز به Kubernetes یا چند دیتابیس فعال را فرض نمی‌کند.

### مسیر نهایی ارتباط

```text
مشتری و کارکنان داخل ایران
          │ HTTPS و نشست مستقل
          ▼
سایت و API مشتری/کارکنان در ایران
          │
          ▼
هستهٔ واحد سفارش و مالی در ایران
     ├── SQL مرجع نوشتن
     ├── فایل خصوصی و PDF و OCR داخلی
     ├── رویداد و صف اعلان داخلی
     └── پیامک و خدمات داخلیِ مجاز
          │ اتصال احراز‌شده و قابل قطع
          ▼
درگاه تلگرام خارج ایران ── تلگرام

پشتیبان رمزگذاری‌شده: یک نسخهٔ مستقل داخلی + نسخهٔ خارجی هنگام دسترسی
```

در پایلوت اولیه ممکن است سایت و ربات به هستهٔ فعلی فرانسه وصل باشند. آن مرحله برای اثبات برابری عملیات است و هنوز پشتیبانی از قطع بین‌الملل محسوب نمی‌شود. انتقال مرجع نوشتن، مرحلهٔ P8 مستقل است.

## ۴. قواعدی که تغییرناپذیر می‌مانند

۱. هر ثبت تجاری شناسهٔ پایدار دارد؛ شمارهٔ پیام یا یوزرنیم، کلید اصلی مالکیت نیست.
۲. مشتری فقط دادهٔ خودش را می‌بیند؛ نقش کارمند هم دسترسی سراسری مالی به‌صورت پیش‌فرض نمی‌دهد.
۳. ارسال دوبارهٔ درخواست، callback، رویداد یا refresh نباید سفارش، پرداخت، موجودی یا فاکتور دوم بسازد.
۴. مجموع حجمِ قطعی و رزروهای معتبر، از ظرفیت همان چرخه بیشتر نشود. دامنه و عمر قفل موقت با رزرو دائمی موجودی فرق دارد.
۵. مبلغ فاکتور از snapshot معتبر قیمت و شیشه ساخته شود؛ تغییر قیمت امروز تاریخچه را تغییر ندهد.
۶. پرداخت تأییدشده با رسید آپلودشده فرق دارد؛ بدهی از فاکتور معتبر و پرداخت معتبر محاسبه شود.
۷. حذف فاکتور اثر مالی یک‌باره دارد؛ انتقال بعدی به موجودی اثر مالی دوم ندارد.
۸. مالک هزینهٔ هدیه با گیرندهٔ فیزیکی هدیه مستقل است؛ بستهٔ هدیه‌دهنده شامل هدیهٔ خروجی نیست.
۹. ارسال فقط اقلام آمادهٔ همان محدوده را می‌بندد؛ فاکتور ناآماده، گیرندهٔ دیگر و بستهٔ بعدی نباید ارسال‌شده شوند.
۱۰. جایگاه داخلی و بهای خرید و گزارش انحصاری مدیر در پاسخ، فایل یا API مشتری افشا نشوند.
۱۱. ثبت عملیات در هسته، به موفقیت ارسال تلگرام وابسته نباشد.
۱۲. تاریخ ثبت، تکمیل، فاکتور، پرداخت، آماده‌شدن و ارسال مستقل‌اند و جانشین یکدیگر نمی‌شوند.
۱۳. گزارش‌ها فقط خواندنی‌اند و مبنای مبلغ، تعداد آیتم، عطر متمایز و بازه را روشن می‌کنند.
۱۴. هیچ آزمون یا اجرای سایه، دادهٔ مالی واقعی، مقصد مشتری یا تنظیمات فعال ربات را تغییر نمی‌دهد.

## ۵. محدودهٔ کامل قابلیت‌ها

پیوست الف شامل **۱۹۰ قابلیت با شناسهٔ مستقل** است. فایل `capability-register.csv` همان فهرست را برای Excel و تقسیم کار دارد. برای هر ردیف، حوزه، نقش، مرحله، معیار پذیرش و محل بررسی در پروژه ثبت شده‌اند. مسئول و لینک شاهد باید هنگام اجرا تکمیل شوند؛ خالی‌بودن آن‌ها به معنی تکمیل‌نشدن است.

قابلیت‌ها در ده حوزه‌اند: هویت؛ رابط؛ کاتالوگ و لیست؛ موجودی؛ فاکتور و پرداخت؛ تبلیغ؛ بسته؛ رهگیری؛ گزارش؛ استمرار خدمت. قابلیت موجود در تلگرام تا زمانی که در وب و حالت قطع خارجی آزمایش نشود، قابلیت تکمیل‌شدهٔ وب نیست.

### مرزهای طراحی رابط

صفحهٔ فروش مانند کانال، کارت عطر و دکمه دارد. حساب مشتری مانند اتاق خصوصی، رویداد سفارش و فاکتور و رسید و گفت‌وگو دارد. اتاق‌های کارکنان مانند «واریز جدید»، «دکانت» و «آماده‌سازی» از صف کار واقعی ساخته می‌شوند. عمل مالی با دکمه یا فرم مشخص اجرا می‌شود؛ متن آزاد مبنای تشخیص خودکار تغییر مالی نیست.

در وب، بستن پنل نتیجه به معنی حذف آدرس یا سابقه نیست. شمارندهٔ unread وب مستقل از تلگرام است. قیمت پروموشن و مهلت از سرور می‌آیند؛ اعلان وب می‌تواند کارت فعال داشته باشد و نیازمند تکثیر پیام در هر ۱۵ دقیقه نیست. قاعدهٔ اعلان تلگرام جدا حفظ می‌شود.

## ۶. هویت، انتقال حساب‌ها و دسترسی

ورود پیشنهادی مشتری: موبایل تأییدشده و نشست وب، با امکان روش بازیابی مستقل مصوب. ورود مدیر: رمز و عامل دوم مستقل از تلگرام؛ کد بازیابی در محل امن و روند ابطال نشست. نبود تلگرام نباید بازیابی مدیر را متوقف کند؛ نبود پیامک نیز باید با روش از پیش ثبت‌شدهٔ مدیر قابل مدیریت باشد. بازیابی مشتریِ فاقد هر روش اثبات، خودکار انجام نمی‌شود.

اتصال اولیه در زمان دسترسی تلگرام: کاربر از حساب فعلی پیوند یک‌بارمصرف کوتاه‌عمر می‌گیرد، موبایل را اثبات می‌کند، نام و خلاصهٔ حساب مقصد را می‌بیند و اتصال ثبت می‌شود. اگر موبایل قبلاً متعلق به حساب دیگر باشد یا چند حساب محتمل باشند، فرایند متوقف و به بررسی مدیر می‌رود. تغییر نام کاربری تلگرام نباید CustomerId را عوض کند.

| نقش | حدود دسترسی وب |
|---|---|
| مشتری | سفارش و بدهی و فایل و آدرس خودش؛ درخواست خرید و رسید و تأیید عکس |
| ادمین فروش | لیست و موجودی و ثبت مجاز برای مشتری؛ استثنای بدهی با دلیل طبق قاعدهٔ فعلی |
| حسابدار | درخواست موجودی، فاکتور و رسید و عملیات مالی مجاز؛ دسترسی انحصاری مدیر ندارد |
| مسئول دکانت | صف، مقدار و گیرنده و لیبل و عکس‌های موردنیاز؛ بدون گزارش بهای خرید |
| مسئول ارسال | آدرس و اقلام مجاز بسته و عکس تأیید و رهگیری؛ بدون تغییر قیمت یا تأیید پرداخت |
| مدیر اصلی | گزارش‌های اختصاصی و نرخ و خرید و مدیریت دسترسی‌ها و تأیید انتشار |

این جدول باید با نقش‌های واقعاً فعال تطبیق و امضا شود. غیرفعال‌کردن کارمند هم در UI و هم سمت سرور و نشست‌های موجود اعمال شود. شماره حساب بانکی با نسخه و زمان اعتبار نگهداری شود؛ تغییرش عملیات حساس مدیر است.

### کنترل‌های امنیتیِ لازم برای اجرا

نشست کوکی به محافظت CSRF نیاز دارد؛ CORS فقط مبادی مصوب را بپذیرد. محدودیت تلاش ورود، قفل موقت، چرخش نشست، ابطال و بازیابی عامل دوم باید آزمون داشته باشند. متن گفتگو و نام فایل هنگام نمایش escape و سیاست CSP تنظیم شود. آپلود با نام مسیر ورودی ذخیره نشود؛ فایل اجرایی و حجم نامعتبر رد و محتوای تصویر/PDF بررسی شود. دریافت تصویر از URL دلخواه نباید دسترسی به شبکه داخلی سرور ایجاد کند. فایل خصوصی فقط با بررسی مالکیت یا امضای کوتاه‌عمر قابل دریافت باشد.

نقش و مجوز مالی فقط سمت سرور تصمیم‌گیری شود. تغییر شماره کارت، انتقال فاکتور پرداخت‌شده، استثنای بدهی، اصلاح نرخ تاریخی و جابه‌جایی هویت دارای ثبت عامل و علت و نسخهٔ قبل/بعد باشند. دادهٔ بانکی و آدرس برای تولید متن هوش مصنوعی خارجی ارسال نشود. سیاست نگهداری و حذف داده و backup با نیاز عملیاتی و الزامات حقوقی تعیین شود؛ حذف ظاهری فاکتور نباید سند حسابداری را بدون سابقه نابود کند.

## ۷. قرارداد فنی عملیات مشترک

مرزهای پیشنهادی: Catalog، SalesReservation، ReadyInventory، Billing، Payments، Fulfillment، Shipping، CustomerAccount، Communications، Reports. در شروع ماژول‌های همان برنامه باشند؛ جداسازی سرویس شبکه‌ای فقط با نیاز اثبات‌شده انجام شود.

هر فرمان شامل شناسهٔ عملیات، ActorId استخراج‌شده از نشست، شناسهٔ موجودیت، نسخهٔ مورد انتظار و دادهٔ معتبر است. CustomerId ارسالی مرورگر به‌تنهایی مجوز مالکیت ایجاد نمی‌کند. قیمت، تخفیف، بدهی، حجم قابل انتخاب و وضعیت ارسال در سرور محاسبه می‌شوند.

نمونهٔ قرارداد پیشنهادی، هنوز پیاده‌سازی‌شده نیست:

```text
POST /api/v2/sales-lists/{cycleId}/reservations
Idempotency-Key: operation-uuid
Body: volumeMl, bottleId, expectedVersion, quoteId
Actor/Customer: از نشست معتبر

GET  /api/v2/me/invoices
POST /api/v2/me/invoices/{invoiceId}/receipts
GET  /api/v2/me/parcels/{parcelId}
POST /api/v2/staff/invoices/{invoiceId}/cancel-selected
POST /api/v2/staff/invoices/{invoiceId}/restock-selected
GET  /api/v2/owner/customers/{customerId}/finance
```

کلید عملیات برای همان عامل و همان payload معتبر است؛ استفادهٔ همان کلید با payload متفاوت خطا بدهد. تعارض نسخه، ظرفیت تمام‌شده، بدهی و مجوز، خطاهای قابل فهم و مجزا داشته باشند. قطع ارتباط پس از ارسال فرمان، ابتدا با استعلام OperationId حل شود؛ مرورگر خودکار فرمان جدید نسازد.

قواعد هر عملیات پیش از اتصال وب با fixture مستقل ثبت شوند، از مسیر ربات و سرویس مشترک نتیجهٔ برابر بدهند، سپس مسیر ربات پشت پرچم به سرویس جدید منتقل شود. اجرای سایه فقط محاسبه است و هیچ side effect واقعی ندارد.

## ۸. داده، migration و فایل

در P0 نقشهٔ شناسه‌ها و شمارش و حجم و شاخص‌ها ثبت شود. موجودیت‌های پیشنهادی جدید، بسته به مدل نهایی، شامل اتصال هویت وب، نقش و نشست، Asset مستقل، اتاق و پیام وب، Cursor خوانده‌شدن، OperationReceipt و ChannelDelivery هستند. اگر داده‌ای اکنون داخل Outbox payload است، ابتدا adapter نسخه‌دار برای خواندن آن ساخته شود؛ دادهٔ مالی تاریخی با تبدیل حدسی بازنویسی نشود.

روش schema: **افزودن، تکمیل تدریجی، تغییر مسیر خواندن، تثبیت، سپس حذف در انتشار مستقل**. ستون جدید ابتدا اختیاری یا با مقدار بی‌خطر باشد. backfill قابل ادامه، محدود و دارای cursor و گزارش باشد. ایجاد شاخص یا تغییر جدول بزرگ باید روی نسخهٔ هم‌اندازه آزمایش شود؛ پشتیبانی online index در Edition فعلی فرض نشود.

راه‌اندازی فعلی برنامه مسیر migration دارد. پیش از موازی‌کردن نسخه‌ها، اجرای migration باید به گام کنترل‌شدهٔ انتشار با قفل واحد و نسخهٔ معلوم منتقل شود. این تغییر خودش یک انتشار کوچک با امکان برگشت است. چند نمونهٔ وب و ربات نباید هم‌زمان schema را تغییر دهند.

فایل‌ها: شناسهٔ Asset، مالک، نوع سند، موجودیت و نسخه، hash، اندازه، MIME، مسیر داخلی و وضعیت نسخهٔ تلگرام ثبت شود. محصولِ عمومی با رسید و آدرس و PDF مالی در bucket و سیاست دسترسی مشترک عمومی قرار نگیرد. اعتبارسنجی فایل، محدودیت حجم، بررسی محتوای اجرایی و تبدیل امن لحاظ شوند.

بایگانی: FileIdهای تلگرام در دسته‌های محدود دریافت و به hash و منبع متصل شوند. خطا یا عکس مشکوک در صف بررسی بماند؛ نام مشابه مجوز جایگزینی تصویر عطر دیگر نیست. فایل‌های قبلاً موجود به‌صورت idempotent استفاده شوند. گزارش پوشش فایل‌های ضروری، فایل‌های مفقود و فایل‌های بررسی‌شده تولید شود. همهٔ تاریخچهٔ چت تلگرام از Bot API قابل بازیابی نیست؛ دادهٔ فقط موجود در چت نیازمند خروجی مجاز و تطبیق جداگانه است.

ساخت PDF، فونت فارسی، OCR ضروری و فایل‌های واسط داخل شبکهٔ قابل دسترس داخلی باشند. PDF به snapshot نسخهٔ فاکتور وصل شود. مسیر فعلی n8n/Gotenberg می‌تواند پس از جداسازی ساخت از ارسال و استقرار وابستگی‌های لازم استفاده شود. دانلودهای قدیمی مشتری برای خود او و نسخهٔ معتبر کنترل شوند.

## ۱۰. شبکه و درگاه تلگرام

درگاه خارج ایران Update را با اعتبارسنجی secret می‌گیرد و در صف پایدار خود با حداقل دادهٔ لازم ثبت می‌کند؛ سپس به هستهٔ ایران می‌رساند. وضعیت دریافت شبکه‌ای با تأیید تجاری فرق دارد. پاسخ موفق خرید فقط بعد از commit هسته داده شود. درگاه نمی‌تواند در دیتابیس مالی جداگانه سفارش قطعی بسازد.

اگر مسیر درگاه به ایران قطع شد، عملیات تجاری جدید از تلگرام قطعی اعلام نمی‌شود. فرمان‌های قابل پیگیری با هویت، نسخه و زمان دریافت نگهداری می‌شوند؛ پس از اتصال، قواعد انقضا و ظرفیت و قیمت مجدداً بررسی می‌شوند. پیام قدیمیِ در صف، خودکار تخفیف تمام‌شده یا حجم رزروشده ایجاد نمی‌کند. مدل اخذ تخفیف هنگام قطعی باید با مدیر صریحاً تعیین شود.

ارسال خروجی بر مبنای EventId و ChannelDeliveryId انجام شود. پیش از تلاش شبکه‌ای اثر تلاش ثبت شود. نتیجهٔ نامعلوم به معنی موفق یا مجوز تکرار فوری نیست؛ ممکن است تلگرام پیام را گرفته باشد ولی پاسخ به ما نرسیده باشد. خطای قطعی ۴۲۹ با کل مهلت و خطای قطعی مقصد با صف بررسی حل شود. نگهداری داده و کلید درگاه و مسیر ارتباطی، محدود و قابل ابطال باشند.

## ۱۲. پایلوت با حدود ۱۰۰۰ مشتری

افزایش دسترسی پیشنهادی: کارکنان و حساب آزمایشی → ۵ مشتری داوطلب → ۲۰ → ۵۰ → ۱۰۰ → ۲۵۰ → همهٔ مشتریان واجد شرایط. این گروه‌ها دسترسی به وب را تعیین می‌کنند و **دیتابیس یا موجودی را تقسیم نمی‌کنند**. در P8 جابه‌جایی نویسندهٔ اصلی برای سایت و تلگرام مشترک و سراسری است.

ترکیب پایلوت: مشتری با فاکتور پرداخت‌شده و بدهکار، موجودی، هدیه، پست مشترک، چند بستهٔ باز و سوابق قدیمی؛ دست‌کم حسابدار و مسئول ارسال هم حضور داشته باشند. مشتری با حساب مبهم تا رفع ابهام وارد بخش نوشتنی نشود.

پیشنهاد اولیه: گروه ۵ و ۲۰ نفر هرکدام حداقل یک چرخهٔ کاری کامل، گروه ۵۰ و ۱۰۰ نفر حداقل ۴۸ ساعت و گروه ۲۵۰ نفر حداقل ۷ روز شامل یک نوبت صدور و ارسال واقعی پایش شوند. عبور تابع شواهد است، نه صرف سپری‌شدن زمان. مدیر می‌تواند دورهٔ مشاهده را بیشتر کند؛ مغایرت بازِ حیاتی اجازهٔ کوتاه‌کردن ندارد.

برای هر گروه، ویژگی‌های مجاز، فهرست حساب‌ها، مسئول پاسخ‌گویی، راه ارتباط داخلی و روش بازگشت اعلام شود. آموزش شامل تفاوت «در حال ثبت»، «رزروشده»، «فاکتورشده»، «پرداخت‌شده» و «ارسال‌شده» است. موفقیت کانال تلگرام نباید جای وضعیت واقعی عملیات نمایش داده شود.

## ۱۴. پایش، بار و معیار توقف

در P0 نرخ درخواست، peak هم‌زمانی، زمان پاسخ، خطای ثبت، اندازهٔ دیتابیس و log، رشد فایل، دیسک، CPU، RAM و طول صف به مدت متناسب با یک چرخهٔ فروش اندازه‌گیری شوند. ۱۰۰۰ مشتری فعال به معنی ۱۰۰۰ اتصال هم‌زمان نیست.

هدف آزمایش اولیهٔ پیشنهادی، قابل اصلاح پس از baseline: ۲۰۰ نشست هم‌زمان، ترکیب واقعی مرور/خرید/فایل، ۵۰ درخواست کاربردی در ثانیه برای ۱۵ دقیقه و فشار دست‌کم دو برابر اوج مشاهده‌شده. تعداد نهایی بر اساس داده و هزینه مصوب می‌شود. برای هزار مشتری هم‌زمان، آزمون مستقل لازم است.

هدف موقت: P95 خواندن کمتر از یک ثانیه و ثبت داخلی کمتر از دو ثانیه، بدون زمان خدمات بیرونی؛ خطای فنی کمتر از ۰٫۱٪. این‌ها تعهد اثبات‌شده نیستند. برای عملیات مالی، برابری تا واحد پول تعریف‌شده و شمارش دقیق لازم است؛ درصد خطا جای مغایرت مالی را نمی‌گیرد.

**توقف فوری قابلیت نوشتنی:** هر اضافه‌فروش، فاکتور یا پرداخت تکراری، نشت حساب دیگر، تغییر گیرندهٔ هدیه، یا مغایرت پولی بدون توضیح. خطای فنی بیشتر از ۰٫۵٪ برای ۵ دقیقه یا بدترشدن P95 بیش از ۲۰٪ نسبت به baseline برای ۱۰ دقیقه نیز ماشهٔ توقف پیشنهادی است. حداقل حجم نمونه و هشدارِ ترافیک کم جدا تعریف شوند؛ مسئلهٔ حیاتی منتظر پرشدن نمونه نمی‌ماند.

پایش داخلی باید بدون ابزار خارجی قابل دیدن باشد. برچسب correlation برای عملیات و رویداد و نسخه ثبت شود؛ رمز، توکن، رسید بانکی، آدرس کامل و متن حساس در لاگ عمومی قرار نگیرند. رشد صف مالی، تحویل نامعلوم، نرخ retry، تأخیر پیامک و عقب‌ماندگی پشتیبان هشدار داشته باشند.

### بستهٔ انتشار و حفظ تغییرات دیگر

پیش از انتشار، شناسهٔ commit و hash فایل‌های فعال و image و نسخهٔ schema و پیکربندیِ بدون افشای راز با آخرین ثبت انتشار تطبیق شوند. اگر تغییر دیگری روی سرور یا شاخه وجود دارد، انتشار متوقف و اختلاف ابتدا شناسایی و با حفظ هر دو تغییر ادغام شود؛ reset یا جایگزینی کور مجاز نیست. نسخهٔ بازگشت، سورس و وابستگی‌ها و دستور اجرا کنار گزارش انتشار نگهداری شوند. Git پشتیبان دیتابیس یا فایل‌های مشتری نیست؛ backup داده هم پشتیبان سورس و تنظیمات انتشار محسوب نمی‌شود.

نسخهٔ اول وب روال فعلی کارت‌به‌کارت، رسید و تأیید حسابدار را پوشش می‌دهد. درگاه پرداخت آنلاین پس از تصمیم مدیر با callback امضاشده، استعلام و idempotency و تطبیق مستقل اضافه می‌شود و پیش‌نیاز مهاجرت همهٔ مشتریان نیست.

## ۱۵. سناریوی انتقال production به ایران

### پیش از پنجرهٔ انتقال

- مدیر، مسئول فنی و حسابدار زمان و روش اطلاع‌رسانی را تأیید کنند.
- مقصد با نسخه و schema سازگار، فایل و گواهی و DNS و مانیتورینگ داخلی آماده باشد.
- اندازه و روش انتقال SQL و رسانه و مدت freeze روی دادهٔ هم‌اندازه تمرین شود.
- انتقال اولیهٔ فایل و دیتابیس فقط برای تمرین یا مقصد غیرنویسنده انجام شود.
- روش تشخیص نویسندهٔ فعال و fencing سرور قبلی آماده باشد؛ صرف TTL یا تغییر DNS کافی نیست.
- ingress تلگرام و صف داخلی، Updateهای پذیرفته‌شده و نتیجهٔ نامعلومشان را پایدار ثبت کنند.
- backup دارای checksum و بازیابی واقعی، و فهرست عملیات و رویدادهای تا نقطهٔ برش آماده باشد.

### حین انتقال

۱. نوشتن جدید در تمام مسیرها، ربات، API قدیمی، وب، worker مالی و کار ادمین در یک نقطهٔ کنترل‌شده freeze شود. پاسخ به مشتری «ثبت موفق» نباشد مگر ثبت قبلاً قطعی شده باشد.
۲. عملیات جاری به پایان برسند یا به‌طور صریح تعیین تکلیف شوند؛ صف و OperationId و offset ثبت شوند.
۳. writer قبلی fence شود؛ workerهای هر رویداد فقط در محل مجاز فعال باشند.
۴. آخرین تغییرات با روش سازگار SQL منتقل شوند. استفاده از replication یا Availability Group در SQL Express فرض نشده است؛ روش واقعی انتقال و recovery model باید جدا تأیید شود.
۵. تطبیق دقیق مالی، ظرفیت و رکوردها و فایل‌های ضروری انجام و مقصد تک‌نویسنده فعال شود.
۶. مسیر همهٔ کانال‌ها به همان هستهٔ ایران وصل شود؛ سپس gate نوشتن باز شود.
۷. پایش و تطبیق و شمارش صف‌ها به‌صورت پیوسته ادامه یابد. سرور قدیمی تا پایان تثبیت، مرجع نوشتن نیست.

مدت توقف ثبت فقط پس از تمرین اعلام می‌شود. از قبل نباید وعدهٔ بازهٔ مشخص یا توقف صفر داد. حین freeze کاربر می‌تواند دادهٔ موجود را بخواند؛ تأیید خرید قطعی به پایان انتقال وابسته است.

### چک‌های تطبیق پیش از بازشدن نوشتن

- تعداد و شناسهٔ مشتری، سفارش، فاکتور و پرداخت و رویداد، و بیشترین نسخه/زمان هم‌خوان باشند.
- جمع مبلغ فاکتور به تفکیک وضعیت، جمع پرداخت تأییدشده، بدهی خالص و مالک فاکتور برابر باشند.
- حجم و ظرفیت هر چرخه، رزرو موجودی، سفارش شخصی و هدیه و پیوند به بسته برابر باشند.
- شماره فاکتور، قیمت و مبلغ شیشه و snapshot تخفیف و نرخ تاریخی عوض نشده باشند.
- دارایی‌های ضروری با hash و مجوز، و فایل‌های باقی‌مانده با فهرست استثنا مشخص باشند.
- ترتیب و رسید رویداد و اعلان و انتخاب‌های دستی رهگیری و بسته‌های ارسال‌شده حفظ شوند.

برگشتِ دیتابیس بعد از نوشتن جدید یک عملیات انتقال معکوس داده است و نیاز به تمرین و تأیید دارد. دامنه و IP قدیمی نباید writer دوم ایجاد کنند. برای تراکنش پذیرفته‌شدهٔ برنامه‌ریزی‌شده، هدف عدم از دست‌رفتن هیچ ثبت تأییدشده است. در حادثهٔ ناگهانی، RPO و RTO تابع معماری پشتیبان هستند.

## ۱۷. پشتیبان، ظرفیت و بازیابی

هدف پیشنهادی اولیهٔ حادثه، RPO حداکثر ۱۵ دقیقه و RTO حداکثر ۶۰ دقیقه است؛ تا بازیابی واقعی روی اندازهٔ فعلی و تحت قطع خارجی اثبات نشود، تعهد سرویس نیست. روش full/differential/log به recovery model، Edition، حجم و ابزار زمان‌بندی بستگی دارد. SQL Express نبود SQL Agent را با زمان‌بند مناسب جبران می‌خواهد؛ زنجیرهٔ log بدون تنظیم و آزمون مفروض نیست.

یک نسخهٔ داخلی خارج از میزبان اصلی برای قطع بین‌الملل لازم است. نسخهٔ خارجی برای خرابی گسترده مفید است ولی مسیر بازیابی اضطراری داخلی به آن متکی نمی‌شود. رمزگذاری، نگهداری کلید بازیابی، محدودیت دسترسی، نسخه‌بندی فایل و دورهٔ نگهداری باید مصوب شوند. تغییر یا پاک‌کردن backup فعلی بخشی از ساخت وب نیست.

SQL Express سقف هر دیتابیس ۱۰ GiB دارد؛ اندازهٔ data با log و backup و فایل تفاوت دارد. آستانهٔ اقدام پیشنهادی پیش از ۸ GiB است. باید از هم‌اکنون رشد تصاویر ذخیره‌شده داخل DB و دادهٔ پیام و audit بررسی شود. تبدیل Edition یا تغییر موتور دیتابیس در همان نوبت انتقال وب انجام نشود. نیاز به index، RAM، دیسک، IOPS و پهنای باند پس از آزمایش بار تعیین شود؛ نسبت‌دادن اندازهٔ سرور به تعداد اسمی مشتری کافی نیست.
