# قرارداد خواندن فاکتورهای مشتری در وب

مسیر Application خروجی ساختگی تولید می‌کند و «حساب من» در زمان ساخت پیش‌نمایش از همان خروجی استفاده می‌کند. اتصال زنده به HTTP endpoint، نشست و adapter دیتابیس وابسته است. API و گزارش مالی تلگرام فعلی تغییری نکرده‌اند. عبور P0/P2 یا برابری production ادعا نمی‌شود.

## مرز دسترسی

`CustomerInvoiceReader.ReadMyInvoicesAsync` شناسهٔ مشتری را فقط از `CurrentWebActor` می‌گیرد؛ پارامتر CustomerId/username از مرورگر ندارد. actor باید قبلاً از session معتبر و directory جاری ساخته شده باشد. مشتری غیرفعال، نقش بدون Customer و هویت خالی پیش از فراخوانی store رد می‌شوند. store موظف است مالک مالی **فعلی** را بخواند، نه مالک قبلی پس از انتقال یا گیرندهٔ فیزیکی هدیه. اگر حتی یک سطر متعلق به دیگری بازگرداند، گزارش کامل متوقف می‌شود.

خروجی whitelist فقط فاکتور، اقلام مالی و خلاصه دارد؛ آدرس، موبایل، شناسهٔ تلگرام، CustomerId، نقش، جایگاه فیزیکی، بهای خرید و اطلاعات کارت در DTO نیستند. فاکتور هدیهٔ پرداخت‌کننده با اقلام بستهٔ گیرنده موضوع جداست؛ این قرارداد گزارش بسته یا مالکیت فیزیکی هدیه را پیاده نمی‌کند. فایل PDF خصوصی هم هنوز endpoint ندارد و باید در هر بار دریافت با مالک جاری بررسی شود.

## مبنای مالی

- فقط InvoiceStatus.Issued/Paid، با فاکتور و سفارش حذف‌نشده و سفارش لغونشده.
- جمع پرداخت‌شده برابر جمع مبلغ فاکتورهای Paid است؛ مانند گزارش فعلی، وجود Paid در واردات قدیمی به ساختن ردیف پرداخت جعلی وابسته نیست. `confirmedPayments` همچنان فقط پرداخت‌های واقعاً Confirmed را نشان می‌دهد و در فاکتور Paid قدیمی می‌تواند صفر باشد؛ UI نباید آن را به‌تنهایی نشانهٔ پرداخت‌نشدن فرض کند.
- بدهی فاکتور Issued برابر `max(0, TotalAmount - مجموع پرداخت‌های Confirmed حذف‌نشده)` است. Pending/Rejected/Refunded/Cancelled کم نمی‌شوند. این مدل رویداد مالی جدید یا credit/wallet ایجاد نمی‌کند.
- پرداخت تأییدشدهٔ فاکتورهای باز بدون clamp به مبلغ فاکتور نمایش داده می‌شود؛ اضافه‌پرداخت بدهی منفی ایجاد نمی‌کند و تعیین تکلیفش به حسابداری تعلق دارد.
- قیمت از snapshot تاریخی است؛ نرخ/پروموشن/قیمت امروز ورودی این reader نیست. مقدار اعشاری موجودی و مبلغ اعشاری بدون تبدیل به float حفظ می‌شوند.
- چند فاکتور فعال برای یک سفارش، شناسه یا پرداخت تکراری، payment مشترک بین دو سفارش، مبلغ منفی تأییدشده، سطرهای ناقص یا عدم برابری جمع عطر و شیشه با کل فاکتور، گزارش را متوقف می‌کنند. کد این مرحله دادهٔ قدیمی را اصلاح یا حدس نمی‌زند. adapter آینده باید موارد legacy را با حسابداری تطبیق دهد.

این قواعد روی fixture با فرمول مستقل گزارش فعلی `CustomerInvoiceFinanceService` مقایسه شده‌اند؛ خود سرویس فعلی تعویض نشده و مقایسهٔ دادهٔ واقعی انجام نشده است.

## صفحه‌بندی و دقت

اندازهٔ صفحه ۱ تا ۵۰، پیش‌فرض ۲۰؛ ترتیب زمان صدور نزولی و سپس شناسهٔ فاکتور است. خلاصهٔ مالی و totalCount از **کل snapshot مشتری** هستند، نه فقط صفحهٔ جاری. `asOf` زمان همان snapshot است؛ reader استمرار یک snapshot میان چند درخواست را تضمین نمی‌کند. adapter/endpoint آینده برای حرکت بین صفحات هنگام تغییر داده به نسخه یا continuation سازگار نیاز دارد.

`currency: IRT` یعنی تومان. مبلغ و حجم در JSON رشتهٔ اعشاری لاتین بدون جداکننده‌اند، مثل `"150000"`، `"1.5"` یا `"9007199254740993.25"`. تبدیل این رشته‌ها به `Number` مجاز نیست. `formatExactToman` فقط برای نمایش از BigInt قسمت صحیح و رشتهٔ اعشار استفاده می‌کند و جمع مالی انجام نمی‌دهد. `parseCustomerInvoicesRead` نسخه، واحد، نوع مبلغ، شناسه‌ها و سازگاری صفحه‌بندی را بررسی و فیلد اضافی را به component props منتقل نمی‌کند؛ این validator جایگزین امنیت سمت سرور نیست.

پیش‌نمایش «حساب من» خلاصه و فهرست فاکتورها را از خروجی ساختگی صفحهٔ اول می‌خواند. فیلتر رابط روی همین صفحه اعمال می‌شود و خلاصه از پاسخ کامل می‌آید. تاریخ صدور و زمان وضعیت بر اساس تقویم شمسی و منطقهٔ زمانی تهران نمایش داده می‌شوند. مسیر پیشنهادی بعد از پیاده‌سازی نشست `GET /api/v2/me/invoices?page=1&pageSize=20` است.

## بازتولید شاهد مستقل

```bash
dotnet run --project tools/web-continuity/InvoiceReadFixture --configuration Release -- /tmp/customer-invoice-read.json
cd web/app
npm run typecheck
npm test
```

ابزار generator فقط سه فاکتور ساختگی با GUID ثابت و تاریخ ثابت دارد و هیچ config/DB/مقصدی نمی‌خواند. wrapper فایل شامل `synthetic: true` است. فایل `web/app/test-fixtures/invoice-read.synthetic.json` شاهد مشترک C#/TypeScript است و job فعلی CI برابرماندن آن را با تولید دوباره بررسی می‌کند. .NET DTO از تنظیم JsonSerializerDefaults.Web برای camelCase استفاده می‌کند.

پیش از اتصال واقعی: session/ابطال/CSRF، فعال‌سازی هویت، store مشترک، adapter فقط‌خواندنی با مالکیت جاری و snapshot سازگار، تست SQL انتقال هم‌زمان/پرداخت/حذف، دسترسی فایل، پایش خطای عمومی بدون دادهٔ شخصی، آزمون تطبیق سوابق legacy و gateهای زیرساخت و بازیابی باید تکمیل شوند. aggregate/فایل lookup متکی به username یا CustomerId ادعایی مرورگر پذیرفته نیست.
