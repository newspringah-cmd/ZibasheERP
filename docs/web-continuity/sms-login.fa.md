# ورود مشتری با پیامک — زیرساخت آماده، ارسال واقعی غیرفعال

طبق تصمیم مدیر، ورود اصلی مشتری شماره موبایل و کد پیامکی است؛ یوزرنیم تلگرام روش ورود این مرحله نیست. پنل پیامکی هنوز تهیه نشده است. فرم `/login/` در رابط Next با همان رنگ و سبک تلگرام آماده است؛ شمارهٔ فارسی/عربی و +98/0098 اعتبارسنجی می‌شود، ولی دکمهٔ ارسال کد غیرفعال است. شماره در مرورگر ذخیره یا به شبکه ارسال نمی‌شود.

## بخش‌های پیاده‌شده

- `Application/WebIdentity/CustomerSmsLogin.cs`: قرارداد مستقل پنل پیامکی و directory اتصال تأییدشده، همراه پیاده‌سازی **صرفاً staging و تک‌پردازه** برای چالش. هیچ ثبت DI در API فعلی انجام نشده است.
- موبایل باید به یک CustomerId فعال و یکتا با اتصال تأییدشده اشاره کند. این directory هنوز adapter دیتابیس ندارد؛ ستون Mobile فعلی یا تلفن آدرس، به‌تنهایی اتصال تأییدشده محسوب نمی‌شوند. حساب جدید یا انتقال حساب خودکار ساخته نمی‌شود.
- کد شش‌رقمی تصادفی، اعتبار سه دقیقه، حداکثر پنج تلاش، محدودیت درخواست هر موبایل و هر client و محدودیت اعتبارسنجی، با TimeProvider سمت سرور. ارسال مجدد همهٔ کدهای قبلی آن موبایل را باطل می‌کند.
- فقط HMAC کد در چالش نگهداری می‌شود. چالش قبل از بازگرداندن proof به‌صورت اتمیک مصرف می‌شود و مصرف دوباره یا هم‌زمان موفق نمی‌شود. اتصال جاری و فعال‌بودن مشتری هنگام تأیید دوباره بررسی می‌شود.
- حساب نامعلوم، غیرفعال، اتصال مبهم یا شکست ارسال، شکل پاسخ شروع یکسان دارند. کلید و متن خطای ارائه‌دهنده به caller برنمی‌گردد. چالش‌های غیرمجاز حتی در صورت تطبیق تصادفی کد، proof نمی‌دهند.
- خروجی تأیید فقط proof داخلی CustomerId است؛ کوکی، access token یا نشست و دسترسی کارمند نیست. proof نباید مستقیماً از ورودی HTTP ساخته یا پذیرفته شود.
- `WebReadAccess` سیاست اولیهٔ خواندن فقط حساب/مالک فعلی فاکتور/گیرندهٔ بسته را دارد. هدیه‌گیرنده با پرداخت‌کننده یکی فرض نمی‌شود. گزارش اختصاصی مدیر به principal پیکربندی‌شده و نقش معتبر و MFA کارکنان نیاز دارد؛ SMS مشتری این امتیاز را نمی‌دهد.

## کارهای لازم پیش از فعال‌سازی واقعی

۱. انتخاب و تهیهٔ پنل داخلی با ارسال کد خدماتی/الگویی، تکمیل مجوز خط و الگو و سقف هزینه. خرید و هزینه‌ای در این مرحله انجام نشده است.

۲. ثبت API key و شناسهٔ الگو فقط در secret backend سرور؛ در گفتگو، Git، `NEXT_PUBLIC_*` یا خروجی مرورگر قرار نگیرند. adapter ارائه‌دهنده باید timeout، retry محدود و رویداد عملیاتی بدون موبایل/کد/کلید داشته باشد. قطع سرویس نباید ورود موفق اعلام شود.

۳. ایجاد ساختار persistent برای اتصال تأییدشده و یکتای موبایل به CustomerId، با اثبات از حساب تلگرام قبلی یا بررسی مدیر، ثبت audit و رسیدگی به تعارض. نام، آدرس یا username به‌تنهایی دلیل اتصال نیست. ممیزی قبلی موبایل معتبرِ آمادهٔ ورود در پروفایل‌های فعلی نشان نداده؛ ابتدا enrollment لازم است.

۴. جایگزینی پیاده‌سازی حافظه‌ای با store مشترک اتمیک و محدودیت لبهٔ HTTP برای چند instance؛ کلید client از IP/نشست تحت سیاست trusted proxy سمت سرور استخراج شود، نه body درخواست. محدودیت ظرفیت و زمان اجرای adapter، خاموش‌شدن سرویس و پرشدن store باید آزموده شوند.

۵. endpointهای staging برای start/verify با پاسخ عمومی، جلوگیری از افشای وجود حساب از **زمان پاسخ**، صف ارسال و محدودیت سراسری هزینه. شکل عمومی پاسخ در core وجود دارد، ولی برابری زمان پاسخ HTTP یا provider outage هنوز اثبات نشده است.

۶. ایجاد نشست با امکانات استاندارد ASP.NET Core و key ring پایدار: cookie با Secure/HttpOnly/SameSite، محافظت CSRF، تعویض شناسه پس از ورود، انقضا/ابطال/خروج، بررسی اتصال و نقش جاری و بستن نشست پس از تغییر موبایل/غیرفعال‌شدن. endpoint نباید CustomerId یا نقش ارسالی مرورگر را معتبر بداند. API-key فعلی ERP روش ورود مشتری وب نیست.

۷. اتصال endpointهای فقط‌خواندنی به سرویس مشترک و بررسی مالک فعلی فاکتور و فایل از repository در هر بار خواندن؛ نه CustomerId ادعایی یا مالک تاریخی. سیاست دسترسی به‌تنهایی جایگزین query صحیح و بررسی انتقال/هدایا/لغو و پرداخت جزئی نمی‌شود.

۸. ورود مدیر و کارکنان با MFA مستقل، تأیید هویت و نقش و بازیابی مصوب جدا از SMS مشتری؛ سپس آزمون نفوذ و نشست و پایلوت محدود، مطابق gateهای P0/P2. فرم فعلی و کلاس staging برای نصب production آماده نیستند.

تا انجام این موارد، ورود واقعی، دسترسی مالی واقعی، ارسال پیامک و خرید از سایت بسته می‌مانند؛ ERP فعلی همچنان مسیر کاری فعال است.
