# ورود دوحالته و پیشنهاد شماره از آدرس

فرم ورود اکنون دو انتخاب مستقل دارد: شماره موبایل و آیدی تلگرام. ورودی/خطا هنگام تغییر روش پاک می‌شود. آیدی با/بدون @ یا عددی، از جمله اعداد فارسی و شناسهٔ ۶۴بیتی بدون افت دقت، اعتبارسنجی می‌شود. آدرس لینک تلگرام، markup، صفر و شناسهٔ خارج از محدوده رد می‌شوند. هر دو دکمهٔ ارسال واقعی همچنان غیرفعال‌اند؛ SMS بدون پنل و Telegram بدون اتصال challenge به API/ربات است.

قرارداد backend تلگرام فقط مقصد حساب فعال و یکتا با TelegramUserId پایدار را resolve می‌کند؛ این نتیجه proof یا session نیست. username یا گروه نمی‌تواند مقصد معتبر کد یا نشانهٔ مالکیت باشد. در قرارداد actor، CustomerTelegram از StaffMfa جداست؛ هنوز هیچ نشست واقعی صادر نمی‌شود.

برای پیشنهاد مدیر دربارهٔ آخرین آدرس، سیاست pure backend شمارهٔ آخرین آدرس خود مشتری را فقط پس از احراز هویت همان مشتری پیشنهاد می‌کند؛ آدرس دیگران، حذف‌شده، هدیه، پست مشترک و نوع نامعلوم حذف می‌شوند. شمارهٔ نامعتبر/متعارض در آخرین رکورد با شمارهٔ قدیمی جایگزین نمی‌شود. هیچ موبایلی استخراج یا ثبت یا verified نشده است. اتصال نهایی نیازمند تأیید حساب قبلی و کد SMS و بررسی یکتایی و audit است. adapter آدرس‌های متنی فعلی و migration هنوز ساخته/اجرا نشده‌اند.

شواهد محلی: Application شامل ۱۷۰ آزمون موفق و build با warn-as-error؛ ۸ آزمون Node، ۱ آزمون HTTP با assertionهای متعدد، build بهینه/TypeScript و ۶۶ بررسی مرورگر موفق. نمایش تلگرامی روی موبایل تصویری بازبینی شد. بستهٔ خروجی و manifest فقط دادهٔ ساختگی دارند.

هیچ deploy، endpoint یا DI جدید روی API فعال، ارسال پیامک/تلگرام، session واقعی، خواندن یا نوشتن دادهٔ مشتری و تغییر بک‌آپ/هزینه انجام نشده است. این مرحله شرط عبور P0/P2 را نمی‌بندد. جزئیات فعال‌سازی و قواعد اتصال در [راهنمای ورود](../../sms-login.fa.md) است.
