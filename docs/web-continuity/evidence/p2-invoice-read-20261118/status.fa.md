# مسیر Application برای خواندن فاکتور مشتری

reader فقط‌خواندنی با actor معتبر و CustomerId سمت سرور، snapshot کامل و مالک مالی جاری آماده شد. پاسخ فقط فیلدهای مجاز فاکتور/اقلام/خلاصه را دارد. متن آدرس، هویت تلگرام، بهای خرید، جایگاه و اطلاعات کارت در پاسخ نیستند. store اشتباه بین مشتریان، فاکتور فعال تکراری، payment تکراری و مبلغ ناسازگار به توقف گزارش منجر می‌شوند.

خلاصه بر کل سابقهٔ معتبر همان snapshot محاسبه می‌شود، مستقل از صفحهٔ ۱ تا ۵۰تایی. مبنا روی fixture همان Paid/Issued و Confirmed حذف‌نشدهٔ گزارش فعلی است؛ Paid وارداتی بدون payment جعلی، پرداخت جزئی و اضافه‌پرداخت پوشش داده شده‌اند. UI جدید آینده مبلغ و حجم را به‌شکل رشتهٔ اعشاری می‌گیرد و نمایش با BigInt/string انجام می‌شود. فرمول مالی جدید روی production اجرا یا جایگزین نشده است.

شواهد محلی:

- Application: ۱۸۳ آزمون موفق؛ ۱۳ آزمون جدید reader. build Release با warn-as-error موفق و بدون هشدار.
- TypeScript strict و ۱۳ آزمون Node موفق؛ ۵ آزمون جدید برای قرارداد، دقت عددی و whitelist و صفحه‌بندی.
- ابزار کاملاً synthetic سه فاکتور را در C# تولید کرد و TypeScript همان JSON را خواند. تولید دوباره و مقایسهٔ semantic JSON موفق بود.
- مرحلهٔ parity به CI موجود اضافه شد؛ YAML محلی بررسی شده است، اجرای remote در این گزارش تأیید نشده است.
- رابط و CSS تغییر نکرده‌اند؛ آزمون مرورگر این مرحله دوباره اجرا نشده، چون هیچ مسیر نمایش یا تعامل تازه‌ای به UI متصل نشده است.

محدودیت: این مرحله HTTP endpoint، DI، session، DB adapter، audit واقعی، private-file lookup یا اتصال UI ندارد. consistency/ownership زیر تغییرات هم‌زمان باید در adapter واقعی و SQL staging اثبات شود. ادامهٔ چند صفحه روی snapshot ثابت هنوز نیاز به continuation/version دارد. داده‌های legacy ناسازگار باید بررسی شوند، نه اینکه هنگام گزارش حدس زده شوند. قبل از اتصال باید محاسبه به سرویس مشترک و تطبیق مستقیم با گزارش فعلی و شواهد واقعیِ مجاز برسد. دروازه‌های P0/P2 بازند؛ هیچ customer DB یا مقصد واقعی خوانده یا تغییر داده نشده است.
