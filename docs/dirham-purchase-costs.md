# Private dirham purchase costs

Only the configured stable numeric primary owner (@zahraa_frj) receives or can execute the two private administrator menu controls: «ثبت قیمت خرید درهمی» and «ثبت نرخ روزانه درهم». Callback and message handlers independently require the owner in their own private chat. Purchase prices are not exposed through customer invoices, public captions or customer price calculations.

The manager searches ordinary sales lists by code, Persian/English perfume name or catalog name. Results include stored perfume photographs, Persian/English names, code, bottle volume and any purchase price already recorded. Five results per page with previous/next controls allow access to further matches. After selection, enter the AED price of one complete bottle of that list's volume. Confirm explicitly before storage. Invalid, expired, cancelled and stale confirmations cannot create entries. Selling prices and customer invoices are unchanged.

Exchange rates are toman per one AED (not rials), up to four decimal places. Rate confirmations append immutable effective-time records using the application UTC clock. Every rate remains valid until the next confirmed rate, across days and weekends. There is no expiry, daily reset, automatic external rate import or backdating. Completion exactly at a rate timestamp uses that rate. A future rate must never fill a missing earlier interval.

Cost of a completed list = full-bottle AED purchase price × rate valid at its actual completion timestamp, rounded to whole tomans. The existing completion-time resolver uses ClosedDate, or the last eligible confirmed current-bottle request for completed legacy lists. Invoice/report dates are not substitutes for unknown completion time. Unknown price, rate or completion time is labelled, never treated as zero or substituted with today's rate.

Purchase price versions retain selected list ID, exact perfume variant and volume key, AED amount, actor and timestamp. An explicit price or correction for a selected historical cycle can be entered later and will still use its historical completion rate. Matching later cycles may inherit a price recorded before their completion; changes entered for a different later cycle cannot rewrite a previous cycle. Different bottle volumes/concentrations cannot inherit each other's purchase price. Explicit corrections to the selected cycle are intentional and auditable.

The existing owner-only invoiced-list date-range report adds total cost and data coverage for ordinary list cycles, once per cycle, with incomplete lists explicitly excluded from the known-cost subtotal. Inventory invoice counts remain separate; this change does not claim inventory costs or profit. Private purchasing cards for open lists show explicitly labelled estimates with the currently valid rate.

Schema migration `20261103230738_AddDirhamPurchaseCosts` adds only DirhamExchangeRates and PerfumePurchasePrices with positive-amount constraints, temporal indexes and a restrictive reference to SalesLists. There is no financial backfill, sale/invoice mutation or production test data. Confirmation operation IDs and a short database application lock make duplicate writes idempotent. Isolated SQL and fake Telegram tests cover authorization, search/photos, confirmations, numeric parsing, history, completion boundaries, missing rates and variant isolation.
