# ابزارهای مرحلهٔ P0

این ابزارها بخشی از اجرای دفترچه‌اند و وب‌سایت آماده محسوب نمی‌شوند.

## ممیزی مخزن

```bash
python3 tools/web-continuity/collect_repository.py --output /tmp/repository-baseline.json
python3 -m unittest discover -s tools/web-continuity -p 'test_*.py'
```

فقط فایل‌های tracked مربوط به کنترلرها، Program و رجیستر قابلیت‌ها خوانده می‌شوند. فایل env و کلید خوانده نمی‌شود. خروجی شمارش attributeها و declarations است، نه نقشهٔ کامل runtime route و نه اثبات مجوز.

## ممیزی دیتابیس

`Probe` یک برنامهٔ SQL با پرس‌وجوهای SELECT ثابت است؛ AppDbContext یا startup برنامه و migration اجرا نمی‌کند. اتصال و شناسهٔ مدیر از محیط عملیاتی حفاظت‌شده دریافت می‌شوند؛ مقدارشان در فرمان، خروجی یا مخزن قرار نگیرد. Guard نام دیتابیس و حساب غیر sa و مدیر از مقصد اشتباه جلوگیری می‌کند. برای اجرای مجدد باید نسخهٔ probe و مقصد بازبینی و runtime سازگار استفاده شود.

هر query دارای timeout ده ثانیه، زمان انتظار قفل دو ثانیه و اولویت deadlock پایین است؛ زمان کل queryها محدود است. آمار snapshot تراکنشی منجمد نیست و جای تطبیق مالی زمان مهاجرت را نمی‌گیرد. فقط آمار تجمیعی صادر می‌شود. خواندن مقدار Mobile/TelegramId/Username فقط در حافظه برای طبقه‌بندی است؛ مقدارهای شخصی خارج نمی‌شوند. `ApplicationIntent.ReadOnly` به‌تنهایی تضمین مجوز read-only نیست؛ در اجرای فعلی، عدم نوشتن ناشی از کد SELECT ثابت و نبود مسیر نوشتن است. در محیط ممیزی مستقل، principal دارای SELECT محدود ترجیح دارد.

این برنامه برای production migration یا ایجاد حساب ورود کاربرد ندارد. خاموش‌کردن guard، قرار دادن connection string در shell history، راه‌اندازی نسخهٔ API برای اجرای probe یا استفاده از sa مجاز نیست. خروجی خطا و شواهد خام در فضای خصوصی عملیاتی نگهداری شوند. تست‌ها مستقل از سرور و بدون دریافت اطلاعات مشتری‌اند.

## تمرین بازیابی با دادهٔ مصنوعی

```bash
python3 -m unittest discover -s tools/web-continuity -p 'test_*.py'
python3 tools/web-continuity/rehearse_fixture_restore.py --output /tmp/fixture-restore.json
```

اگر محیط توسعه خاموش است، فقط با `--start-development-container` می‌توان همان کانتینر توسعه را روشن کرد. مقصد ثابت `zibashe-onboarding-sql` با label توسعه، Docker socket محلی و پورت `127.0.0.1:14333` الزام است. کانتینر تولید یا پورت عمومی رد می‌شوند. دو دیتابیس با نام UUID تازه، جدول مصنوعی و backup خودش ساخته می‌شوند؛ CHECKSUM، VERIFYONLY، RESTORE و CHECKDB و تطبیق داده اجرا و سپس فقط منابع ساخته‌شده پاک می‌شوند. فایل بک‌آپ واقعی، نام دیتابیس ورودی، WITH REPLACE یا دیتابیس مشتری پذیرفته نمی‌شود. حساب sa فقط **داخل کانتینر توسعهٔ تأییدشده** و بدون نمایش رمز استفاده می‌شود؛ این ابزار مجوز استفاده از sa روی production نیست.

زمان ثبت‌شده برای fixture کوچک، RTO واقعی ERP نیست. خروجی `production_backup_tested=false` باید حفظ شود. برای تمرین بک‌آپ واقعی به مقصد جدا و حفاظت داده و برنامهٔ مصوب نیاز است.

سه اسکریپت shell ممیزی metadata و وضعیت systemd و طبقه‌بندی خطا را فقط روی میزبان موردنظر اجرا می‌کنند؛ خروجی‌ها محتوای بک‌آپ یا کلید یا لاگ خام ندارند. `classify_backup_failures.sh` برای journal به `sudo -n` نیاز دارد. تطبیق کلمه در لاگ تشخیص قطعی آخرین اجرای خاص نیست. خالی‌بودن زمان‌بند کاربر، نبود زمان‌بند سیستمی را ثابت نمی‌کند. موفقیت سرویس هم به‌تنهایی اثبات قابل بازیابی بودن backup نیست.

## guard آمادهٔ آپلود بک‌آپ

`backup_upload_guard.py` یک مؤلفهٔ آزموده‌شده و **هنوز نصب‌نشده روی worker** است: HEAD قبل و بعد، تطبیق metadata و size، جلوگیری از overwrite متفاوت و تکرار کور پس از نتیجه نامعلوم. سیاست retry خود SDK یا multipart را جایگزین نمی‌کند. `omit_expect_header` پیش از امضای درخواست ثبت می‌شود و TLS را تغییر نمی‌دهد. ادغام production فقط با source hash و آزمون واقعی محدود پس از رفع cap انجام شود. فایل‌های اصلی و تنظیمات retention توسط این مؤلفه حذف یا تغییر نمی‌شوند.
